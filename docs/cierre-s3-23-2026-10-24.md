La rendición y el cumplimiento se declaran explícitamente DEMO. Un documento sintético no prueba un gasto ni una entrega real. La revisión humana no se sustituye por una marca automática. ADMIN/REVIEWER revisa rendición; SUPPORT resuelve incidencias; FINANCE opera desembolsos/devoluciones por sus módulos existentes. ADMIN no obtiene FINANCE ni SUPPORT automáticamente. AUDITOR conserva solo lectura incluso combinado con otros roles.

## Reglas y validaciones

- Se conserva el motor del ciclo: alcanzar meta antes de plazo no lo termina; todo-o-nada sin meta exige devolver; flexible con fondos habilita ejecución, no un movimiento automático. Se usan pagos DEMO confirmados y devoluciones completadas, no resultados optimistas del frontend.
- Las escrituras requieren sesión, origen/cabecera de mutación, permiso vigente, titularidad/representación actual o independencia, consentimiento DEMO, motivo de 20–500 caracteres, versión y clave idempotente. Se revalida acceso después de esperas. El límite compartido de escrituras sigue vigente.
- Los avances se registran por su API existente: estados/porcentaje entero 0–100, responsable, fechas reales válidas y no futuras. Completar requiere 100% e inicio/fin. La representación institucional utiliza miembro actual, incluidas bajas futuras; cambiar representación toma el bloqueo del padre organización. Un antiguo autor no conserva gestión institucional sin representación.
- El cumplimiento mínimo requiere aporte confirmado con recompensa y saldo no devuelto completamente. Una devolución parcial no elimina esa obligación. Fecha de ejecución real, no futura; evidencia privada propia; un cumplimiento terminal no se sobrescribe. No se modifica el pago ni se libera dinero al declarar cumplimiento.
- Compatibilidad: un cumplimiento histórico ya FULFILLED sin el vínculo nuevo permite adjuntar respaldo; debe conservar exactamente su fecha, responsable y notas originales. No se reescribe la entrega para hacer pasar el cierre.
- Rendición: período real desde el día de inicio de ejecución hasta hoy en Bolivia; inicio no posterior al fin. Narración de 20–5000 y explicación de variaciones de 20–2000 caracteres, también cuando no hubo variaciones. Se rechazan blancos, HTML, controles invisibles y sustitutos Unicode aislados; Ñ y acentos son válidos.
- Máximo 100 gastos. Cada gasto lleva categoría activa desde PostgreSQL, descripción de 10–300, importe positivo decimal exacto (numeric(14,2), no flotante; máximo 999999999999,99), fecha dentro del período y 1–3 evidencias privadas distintas. Si vincula partida, esta debe pertenecer a la misma campaña y categoría. La interfaz permite un documento por gasto; la API admite hasta tres. Gasto no previsto exige la explicación del informe; no se inventa una nueva categoría.
- La suma exacta de gastos debe coincidir con desembolsos completados; no se permite escribir recibido/gastado/saldo, aprobación ni moneda desde el cliente. Se calculan en servidor. Un remanente no desaparece por poner saldo cero: si no está justificado/resuelto el cierre se bloquea. Los totales no se redondean silenciosamente para hacerlos caber en la tabla oficial.
- Presentar no aprueba. Mientras un informe está pendiente no se presenta otro. Un informe observado se reemplaza por otra versión inmutable, conservando el anterior. Solo se revisa el último; no hay autoaprobación ni aprobación por un miembro de la organización beneficiaria.
- La revisión comprueba identidad DEMO vigente, obligaciones, fondos, evidencia y huella de avances/recompensas. Cambiar resultados después de enviar/aprobar invalida el cierre hasta una nueva revisión. Un desembolso posterior también exige una rendición actualizada.
- Evidencias: propósito propio `CLOSURE_EVIDENCE`, privadas, PDF/PNG/JPG/WebP de hasta 5 MB y comprobación básica de firma. No sustituye antivirus ni autenticidad documental. Se descargan solo desde el vínculo autorizado del ciclo; no quedan públicas ni disponibles por UUID a terceros. SUPPORT/FINANCE no heredan documentos/narraciones de rendición por consultar requisitos; titular/representante, revisión y AUDITOR acceden según permiso actual. No se elimina una evidencia enlazada.
- La resolución mínima de soporte rechaza un caso propio o de otra campaña, respeta independencia y no permite saltarse una disputa financiera. No crea devoluciones ni elimina reservas. Crear incidencia se serializa con el cierre; el MVP no añade obligaciones nuevas a una campaña ya cerrada y conserva la consulta histórica.
- Cerrar exige que no existan pagos, conciliaciones, reservas, disputas, incidencias ni desembolsos pendientes. En ejecución: actividades/hitos completos, recompensas exigibles cumplidas y última rendición independiente aprobada, vigente, respaldada y con saldo cero. Sin fondos o con devolución completa por fracaso/cancelación se conserva la ruta de cierre sin inventar gastos.
- Cancelar tras liberar fondos continúa escalando a un caso: resolver un mensaje no recupera el dinero ni autoriza una cancelación ficticia. No existe cierre forzado para esconder un faltante; ese estado es un bloqueo de negocio, no una confirmación automática de éxito.

| Ruta relativa a `/api` | Uso |
| --- | --- |
| `GET me/campaign-closure/:id?page=1` | Preparación propia autorizada. |

Todos los POST tienen `{action, expectedVersion, requestKey, reason, demoConsent: true, data}`. `data` acepta únicamente campos propios de la acción; no se aceptan aprobaciones/importes derivados suministrados por el navegador. Una repetición con la misma clave y contenido no duplica efectos; contenido distinto o versión antigua devuelve 409. Error de red no se presenta como éxito.

## Tutorial de cierre

1. Actualizar una V2 existente según README §33 (respaldo, compilación y migraciones; no restaurar el SQL sobre sus datos). En una copia nueva seguir primero §3. Esperar 27 migraciones y readiness correcto; activar DEMO explícitamente.
2. Completar campaña, revisión/publicación, aporte DEMO y fin de recaudación como antes. ADMIN ajeno inicia ejecución; FINANCE y creador completan el desembolso por sus pantallas existentes.
3. Creador: **Mis proyectos → Ciclo y desembolsos → Preparar cierre**, `/mis-proyectos/:id/cierre`. El detalle permite volver a avances y consultar bloqueos.
4. Registrar actividades/hitos en **Avances**. Para recompensas exigibles, adjuntar evidencia sintética, indicar fecha real y motivo, elegir **Registrar cumplimiento DEMO** y confirmar. Sin recompensas no se solicita una entrega inventada.
5. Resolver incidencias abiertas. SUPPORT usa **Preparar cierres DEMO**, `/administracion/cierre-campanas`, abre la campaña y resuelve solo casos no financieros. Las disputas usan su módulo y, si procede, el flujo financiero separado.
6. Creador presenta el período, resultados, explicación de variaciones y gastos exactos con documentos. Elegir **Presentar rendición final DEMO**, motivo y confirmación. Se conserva como SUBMITTED y no se edita mientras espera revisión.
7. ADMIN/REVIEWER independiente abre **Preparar cierres DEMO**, consulta documentos y decide **Aprobar rendición final** o **Solicitar correcciones** con motivo. El titular vuelve a presentar una nueva versión si fue observada. Aprobar no cierra ni mueve fondos.
8. ADMIN abre **Ver bloqueos y decidir el ciclo**. Solo si no existen bloqueos aparece **Cerrar campaña**. Confirmar con motivo. El servidor vuelve a comprobarlo todo y deja CLOSED, fecha e historial; no quedan botones para reabrir/editar resultados terminales.
